Part I

Getting Started & App Bootstrapping

01 Platform Architecture Overview

Bifrost strictly separates the **Control Plane** (MongoDB central storage holding application secrets, webhook tokens, custom domain mappings, and staff roles) from the **Tenant Data Plane** (independent PostgreSQL/Supabase databases holding end-user records, transactions, and content). 

                  +-----------------------------------+
                  |      Bifrost Control Plane        |
                  |  - App Registry (Client IDs)      |
                  |  - Webhook Secrets (HMAC Keys)    |
                  |  - Vault Secrets (Encrypted API)  |
                  |  - MongoDB (Central Storage)      |
                  +-----------------+-----------------+
                                    |
                                    | Proxies Writes Live
                                    v
                  +-----------------------------------+
                  |       Tenant Data Plane           |
                  |  - PostgreSQL / Supabase Tables   |
                  |  - users, payments, entitlements  |
                  +----------------+------------------+

02 Python SDK & Environment Injection

Downstream Python client applications should use the `bifrost_client` SDK to bootstrap secrets into `os.environ` at boot time, or use `bifrost_ai` for Google Vertex AI / Cloud Vision client factories.

Bootstrap Credentials (`bifrost_client`):
from bifrost_client import BifrostClient

# Bootstrapping credentials into os.environ at client startup:
BifrostClient(
    client_id="ministry_exam_prep",
    webhook_secret="your_configured_webhook_secret",
    bifrost_url="https://bifrost.wkc.kh"
)
# Automatically decrypts and injects DB_CONNECTION, JWT_SECRET, etc. into os.environ

03 Direct HTTP Config Fetching

Non-Python applications can query the Bifrost config REST endpoint directly during startup.

GET /api/v1/config
Headers Required: `X-Client-ID: ` and `X-Webhook-Secret: ` 
curl -X GET https://bifrost.wkc.kh/api/v1/config \
  -H "X-Client-ID: ministry_exam_prep" \
  -H "X-Webhook-Secret: your_webhook_secret_key"

04 Service Segmentation & Feature Flags

Each registered tenant can toggle individual services on or off inside their MongoDB application document using the `enabled_services` dictionary:

Service Flag Default Description
secrets_vault true Allows client applications to fetch decrypted configuration keys.
payment_bot true Enables Telegram receipt submission & SLA alert bots.
oauth_sso true Enables Google/Facebook OAuth SSO login endpoints.
sms_otp true Enables Phone SMS OTP verification endpoints.
email_otp true Enables Email verification code endpoints.

warning If a service is set to false, the Bifrost gateway automatically rejects calls to those endpoints with a 403 Forbidden response.

Part III

Webhook Integration & Security

09 Webhook Dispatch System

Whenever a customer payment is approved, rejected, or refunded in the console, Bifrost triggers a `POST` webhook request to the client application's configured `webhook_url`.

10 HMAC-SHA256 Signature Verification

Client applications **must** verify the `X-Bifrost-Signature` header before processing webhook entitlement payloads to prevent forged requests.

Python Flask Signature Verification Example:
import hmac
import hashlib
from flask import Flask, request, abort

app = Flask(__name__)
WEBHOOK_SECRET = b"your_configured_webhook_secret"

@app.route('/bifrost-webhook', methods=['POST'])
def handle_webhook():
    signature = request.headers.get('X-Bifrost-Signature')
    if not signature:
        abort(403, "Missing signature header")
        
    expected_signature = hmac.new(
        WEBHOOK_SECRET,
        request.data,
        hashlib.sha256
    ).hexdigest()

    if not hmac.compare_digest(expected_signature, signature):
        abort(403, "Invalid HMAC signature")

    payload = request.get_json()
    event_type = payload.get('event')
    # Process entitlement change...
    return "OK", 200
Node.js Express Signature Verification Example:
const crypto = require('crypto');
const express = require('express');
const app = express();

const WEBHOOK_SECRET = "your_configured_webhook_secret";

app.post('/bifrost-webhook', express.raw({ type: 'application/json' }), (req, res) => {
    const signature = req.headers['x-bifrost-signature'];
    const expectedSignature = crypto
        .createHmac('sha256', WEBHOOK_SECRET)
        .update(req.body)
        .digest('hex');

    if (!crypto.timingSafeEqual(Buffer.from(signature || ''), Buffer.from(expectedSignature))) {
        return res.status(403).send('Invalid signature');
    }

    const payload = JSON.parse(req.body.toString());
    // Handle payload...
    res.status(200).send('OK');
});

Part IV

CMS Onboarding & Database Proxying

12 Database Proxy Architecture

The console holds no customer data locally. It connects directly to your PostgreSQL database using `ThreadedConnectionPool` and context managers (`get_tenant_db`). Queries are executed dynamically to remain resilient to minor schema deviations.

13 The 3-Step CMS Onboarding Wizard

When launching the Backoffice console for a new application (`/backoffice/app//onboarding`), a 3-step setup wizard initializes the workspace:

1
Connect Database

Input PostgreSQL connection string. Connection details are encrypted before saving.

2
Smart Schema Detection

Introspects schema, auto-hides plumbing tables (`migrations`, `tokens`, `logs`), and proposes friendly labels (`users` → `Customers`).

3
Invite Team

Assign staff roles (`content_manager`, `operations`, `admin`) by email before launching.

14 Tenant-Agnostic Queue Schema Mapping

If your tenant database uses custom table or column names, describe them in CMS Settings under `payment_queue` (`cms_config.payment_queue`):

16 Payment Verification Queue & SLA Clock

Every submitted receipt enters the human verification queue. The real age clock monitors progress against the 6-hour SLA promise:

Age < 4h 30m
On Time

Payment is comfortably within the service window.

4h 30m – 6h
Approaching SLA

Alert dispatched to Telegram channel. Deal with immediately.

Over 6h
Breached SLA

Service promise is broken. Priority resolution required.

17 Payment State Machine & Actions

Payments strictly transition between states (`FREE` → `PENDING` → `PREMIUM` / `REJECTED`, `PREMIUM` → `REFUNDED`).

check_circle Approving

Atomically marks payment approved, unlocks track entitlements in Postgres, and triggers client webhooks as one transaction. Duplicate references are rejected.

cancel Rejecting

Requires reason code (`wrong_amount`, `unreadable`, `duplicate_reference`, `other`). Allows customer to re-submit a fresh receipt.

undo Refunding

Allowed only on approved payments. Revokes only the entitlement unlocked by that specific transaction.

18 Exam Question Automated Publish Quality Gate

Publishing exam content (`review` → `published`) is restricted to Admins/Owners and is automatically blocked by the server unless all 4 criteria pass:

check_box Exactly 4 choices defined on the question.
check_box Exactly 1 choice marked as correct.
check_box Bilingual explanations (Khmer & English) present on the correct choice.
check_box Non-empty `source_ref` tracing the question to an official source document.

19 Audit Log & User Suspensions

Every mutation (approvals, rejections, refunds, content edits, manual overrides) is permanently recorded in the immutable audit log with actor ID, timestamp, and before/after JSON diffs. Suspensions lock user accounts while preserving paid entitlements.

20 Operational Safeguards & Guarantees
