Client and staff reference

Bifrost identity, secrets and control plane

Bifrost is a central control plane for application registration, credentials, a secrets vault and identity — while proxying administrative operations live to independent tenant databases. This manual covers onboarding, the SDK, API endpoints, webhook verification and the console operator's manual.

Part I

Getting started and app bootstrapping

01 · Platform architecture

Bifrost separates the control plane — MongoDB, holding application secrets, webhook tokens, domain mappings and staff roles — from the tenant data plane, independent PostgreSQL or Supabase databases holding end-user records, transactions and content. The console stores no customer data of its own. 

+-----------------------------------+
|      Bifrost control plane        |
|  - App registry (client IDs)      |
|  - Webhook secrets (HMAC keys)    |
|  - Vault secrets (encrypted)      |
|  - MongoDB (central storage)      |
+-----------------+-----------------+
                  |
                  |  proxies writes live
                  v
+-----------------------------------+
|        Tenant data plane          |
|  - PostgreSQL / Supabase tables   |
|  - users, payments, entitlements  |
+-----------------------------------+

02 · Python SDK and environment injection

Python clients use the bifrost_client SDK to bootstrap secrets into os.environ at boot, or bifrost_ai for Vertex AI and Cloud Vision client factories. 

from bifrost_client import BifrostClient

BifrostClient(
    client_id="ministry_exam_prep",
    webhook_secret="your_configured_webhook_secret",
    bifrost_url="https://bifrost.wkc.kh"
)
# Decrypts and injects DB_CONNECTION, JWT_SECRET, etc. into os.environ

Non-Python applications can query the config endpoint directly at startup.

GET /api/v1/config Requires X-Client-ID and X-Webhook-Secret headers.

  -H "X-Client-ID: ministry_exam_prep" \
  -H "X-Webhook-Secret: your_webhook_secret_key"

Part III

Webhook integration and security

09 · Dispatch system

When a payment is approved, rejected or refunded in the console, Bifrost POSTs to the application's configured webhook_url.

10 · HMAC-SHA256 signature verification

Verify the X-Bifrost-Signature header before processing any entitlement payload. Compare in constant time — a plain == leaks the signature one byte at a time. 

import hmac, hashlib
from flask import Flask, request, abort

app = Flask(__name__)
WEBHOOK_SECRET = b"your_configured_webhook_secret"

@app.route('/bifrost-webhook', methods=['POST'])
def handle_webhook():
    signature = request.headers.get('X-Bifrost-Signature')
    if not signature:
        abort(403, "Missing signature header")

    expected = hmac.new(WEBHOOK_SECRET, request.data, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, signature):
        abort(403, "Invalid HMAC signature")

    payload = request.get_json()
    event_type = payload.get('event')
    # Process the entitlement change...
    return "OK", 200
const crypto = require('crypto');
const express = require('express');
const app = express();
const WEBHOOK_SECRET = "your_configured_webhook_secret";

app.post('/bifrost-webhook', express.raw({ type: 'application/json' }), (req, res) => {
  const signature = req.headers['x-bifrost-signature'] || '';
  const expected = crypto
    .createHmac('sha256', WEBHOOK_SECRET)
    .update(req.body)
    .digest('hex');

  const a = Buffer.from(signature), b = Buffer.from(expected);
  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) {
    return res.status(403).send('Invalid signature');
  }

  const payload = JSON.parse(req.body.toString());
  res.status(200).send('OK');
});
Note: timingSafeEqual throws when the two buffers differ in length, so check the length first — otherwise a malformed header crashes the handler instead of returning 403.

Part IV

CMS onboarding and database proxying

12 · Database proxy architecture

The console holds no customer data locally. It connects to your PostgreSQL database through a ThreadedConnectionPool and the get_tenant_db context manager, which always returns the connection to the pool and rolls back any transaction the caller left open. Queries are built dynamically so minor schema deviations don't break the console.

13 · The setup wizard

Opening the console for a new application runs a three-step wizard.

  • Connect database — the connection string is encrypted before it is stored.
  • Smart schema detection — hides plumbing tables (migrations, tokens, logs) and proposes readable labels (users → Customers).
  • Invite the team — assign staff roles by email before launching.

If the database is empty, the wizard offers starter schemas instead — exam preparation or storefront — which create a working set of tables in one click.

14 · Tenant-agnostic queue schema mapping

If your tables and columns are named differently, describe them under payment_queue in the schema config. The console validates this at save time, so a bad mapping is a readable error rather than a 500 the first time someone opens the queue. 

{
  "payment_queue": {
    "table": "orders",
    "id": "order_id",
    "subject_key": "customer_id",
    "amount": "total",
    "reference": "ref",
    "receipt": "proof_url",
    "status": "state",
    "open_states": ["awaiting_review"],
    "settled": ["paid", "refunded"],

16 · Payment queue and the SLA clock

Every submitted receipt enters the human verification queue against a 6-hour SLA.

AgeStateWhat happens
under 4h 30mOn time Comfortably within the service window.
4h 30m – 6hApproaching An alert is dispatched to the Telegram channel. Handle immediately.
over 6hBreached The service promise is broken. Priority resolution.

17 · Payment state machine

Payments move FREE → PENDING → PREMIUM or REJECTED, and PREMIUM → REFUNDED.

  • Approving — atomically marks the payment approved, unlocks the entitlement in Postgres and fires the client webhook as one transaction. Duplicate transaction references are rejected.
  • Rejecting — requires a reason code (wrong_amount, unreadable, duplicate_reference, other). The customer may submit a fresh receipt.
  • Refunding — allowed only on approved payments, and revokes only the entitlement that specific transaction unlocked.

18 · Publish quality gate

Moving exam content from review to published is restricted to admins and owners, and the server blocks it unless all four hold:

  • Exactly four choices on the question.
  • Exactly one choice marked correct.
  • Bilingual explanations (Khmer and English) on the correct choice.
  • A non-empty source_ref tracing the question to an official document.

19 · Audit trail and suspensions

Every mutation — approvals, rejections, refunds, content edits, manual overrides and raw SQL — is recorded permanently with actor, timestamp and a before/after diff. Retention is at least one year and there is no TTL on the collection. Suspending a user locks the account while preserving paid entitlements, which are restored on reinstatement.

20 · Core guarantees

  • No plaintext passwords. Passwords are never stored in plaintext and staff will never ask for one.
  • Money moves outside the console. The console records verification decisions; bank transfers and cash refunds happen at the tenant's bank.
  • Nothing is deleted quietly. Every change is logged with full before and after state.
Part VI

SQL Studio

21 · Running raw SQL

SQL Studio runs statements directly against a tenant's PostgreSQL database from the browser, so schema migrations and one-off fixes no longer require opening Supabase Studio. It appears in the console sidebar under Developer for anyone holding db:execute.

  • Multiple statements separated by semicolons run as one batch — a whole migration can be pasted in.
  • Results come back as a table for anything that returns rows, and as an affected-row count for CREATE, DROP, UPDATE and friends.
  • Postgres errors are shown verbatim, including position and hint, rather than being flattened into "query failed".
  • Ctrl/⌘ + Enter runs the editor contents.
GET/backoffice/app/<app_id>/devtools The editor.
POST/backoffice/api/app/<app_id>/devtools/execute Body {"sql": "...", "commit": false}. Both routes require db:execute. 
{
  "kind": "rows",
  "columns": ["id", "email"],
  "rows": [[1, "student@aupp.edu.kh"]],
  "row_count": 1,
  "truncated": false,
  "committed": false,

}

22 · The developer role

Raw SQL is gated behind a single permission, db:execute, which is held by exactly one role: developer. It is not bundled into admin or owner — an owner has to assign it deliberately, under Users & settings.

The role is intentionally narrow rather than a superset of admin. A contractor running migrations has no business approving payments or reading vault secrets, and this way you can grant one without the other. Platform staff (heimdall / pr0meth4us) already hold every permission and so have access as well.

Warning: Business owners, content managers and support staff cannot see the SQL Studio link and are refused by the server if they request the URL directly.

23 · What protects you

There is deliberately no blocklist of dangerous statements. Any such filter is trivially bypassed with DO $$ ... $$ or EXECUTE, and its real cost is convincing people the tool is safer than it is. The protections are structural instead:

  • Nothing commits unless you ask. Statements run inside a transaction that is rolled back unless Commit changes is ticked — so you can run a DELETE and read the row count before meaning it.
  • Every statement is audit-logged before it runs, against your account. A query that takes the database down still leaves a record of who ran it.
  • A 15-second statement timeout. The tenant connection pool is eight connections wide, so one runaway scan would otherwise starve the whole console for that tenant.
  • Results cap at 500 rows, so SELECT * on a large table returns a preview instead of trying to serialise the table.
Warning: None of this prevents a committed DROP TABLE users CASCADE. Treat db:execute as equivalent to production database credentials, because that is what it is. Keep backups.
